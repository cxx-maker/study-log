# 测试流程与缺陷管理

> Day 3（2026-11-14）· W1 测试基本功
> 主题：先搞清测试岗每天在干什么

---

## 一、测试流程六步

| 步骤 | 做什么 | 谁参与 | 产出 |
|---|---|---|---|
| 1. 需求评审 | 挑需求里的歧义、缺失、不可测的地方 | 产品、开发、测试、UI | 评审意见 |
| 2. 测试计划 | 定清测什么、**不测什么**、谁测、什么时候测完 | 测试负责人 | 测试计划 |
| 3. 用例设计 | 把需求拆成一条条可执行的检查项 | 测试 | 用例库 |
| 4. 执行 | 按用例逐条跑，记录通过 / 失败 | 测试 | 执行结果 |
| 5. 缺陷跟踪 | 失败项提单，跟到修复、验证、关闭 | 测试 + 开发 | 缺陷单 |
| 6. 测试报告 | 说明测了什么、发现多少、剩什么风险 | 测试 | 测试报告 |

**核心结论**：六步里真正耗时的只有第 4、5 步，前面全是在「想清楚」。
测试的价值不在手快，在于**想到了别人没想到的那条路径**。

**越早介入越便宜**：评审时改一句话，比上线后改一个功能便宜一百倍。

## 二、缺陷生命周期

```
新建(New) → 指派(Assigned) → 修复(Fixed) → 验证(Verifying) → 关闭(Closed)
```

| 状态 | 谁在操作 | 说明 |
|---|---|---|
| 新建 | 测试 | 填单：标题、复现步骤、预期、实际、严重程度 |
| 指派 | 测试负责人 / 开发经理 | 指给具体开发 |
| 修复 | 开发 | 改完标记已修复，注明改动范围 |
| 验证 | 测试 | 按原复现步骤重跑一遍 |
| 关闭 | 测试 | 验证通过后关单 |

### 三条分叉

- **重开（Reopen）**：验证没修好，或修好但带出新问题 → 退回指派
- **拒绝（Rejected）**：开发认为不是 bug → 测试不认可时须上升，不能自己咽下
- **延期（Deferred）**：本版不修，排到下个版本 → 需要有人拍板

**关键**：只有测试有「关闭权」，但从新建到关闭每一步都要别人配合。

## 三、严重程度 vs 优先级

| | 严重程度 Severity | 优先级 Priority |
|---|---|---|
| 看什么 | 坏了多厉害 | 多急着修 |
| 视角 | 技术 | 业务 |

两个典型例子：

- 首页公司名写错一个字 → 严重程度**低**，优先级**高**（老板明天见客户）
- 深处后台设置页崩溃 → 严重程度**高**，优先级**低**（三个月没人点）

## 四、bug 报告必含 8 项

1. 标题：`模块 - 条件 - 结果`
2. 环境：浏览器 / App 版本、系统版本、测试账号
3. 前置条件：把系统调到能触发 bug 的状态
4. 复现步骤：1. 2. 3.
5. 预期结果：本来应该发生什么
6. 实际结果：实际发生了什么
7. 严重程度 / 优先级
8. 附件：截图或日志

**标题写法对比**

- 差：`登录有问题`
- 好：`登录-手机号含空格-仍可获取验证码`

## 小结

> 测试越早介入越便宜；bug 单写不清楚等于没提。

前置条件的判定标准：**一个不熟悉这个功能的人，照着它就能把系统调到能触发 bug 的状态。**
