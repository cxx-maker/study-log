## Bug 1：手机号校验缺失

```
标题：登录-手机号含空格-仍可获取验证码
环境：App 名称 v1.0 / 手机型号 / 系统版本
前置条件：App 已安装可打开登录页，测试手机号未注册
复现步骤：
  1. 打开 App，进入登录页
  2. 手机号输入框输入「138 0013 8000」（含两个空格）
  3. 点击「获取验证码」
预期结果：提示「手机号格式不正确」，不发送验证码
实际结果：未做任何格式校验，直接提示发送成功并收到短信
严重程度：中（校验缺失，可能导致后续号码匹配异常、短信计费浪费）
优先级：中（用户高频路径）
附件：截图1 输入带空格后的界面；截图2 验证码发送成功提示
```

**要点**：空格属于「格式错误」，不是「位数错误」。预期必须写清是哪种提示。

## Bug 2：已下架商品仍可增加数量

```
标题：购物车-商品已下架-仍可增加购买数量
环境：App 名称 v1.0 / 手机型号 / 系统版本
前置条件：已登录；购物车内有 1 件商品；该商品已在后台被下架
复现步骤：
  1. 登录后进入购物车页
  2. 确认该商品已显示「已失效」状态
  3. 点击该商品数量旁的「+」
预期结果：已下架商品「+」按钮置灰不可点，或点击后提示「商品已下架」
实际结果：数量由 1 变为 2，无任何提示
严重程度：中（页面未拦截，结算环节是否拦截需二次验证）
优先级：中
附件：截图1 已下架商品状态；截图2 点击后数量变为 2
```

**要点**：「结算环节是否拦截需二次验证」——这句话说明测试想过影响范围，而不只是照抄页面现象。

## Bug 3：订单列表分页失效

```
标题：订单列表-点击第2页-仍显示第1页数据
环境：App 名称 v1.0 / 手机型号 / 系统版本
前置条件：已登录；账号下订单总数 ≥ 11 条（保证存在第 2 页）
复现步骤：
  1. 进入「我的订单」列表
  2. 确认底部页码显示第 1 页，共 5 页，每页 10 条
  3. 点击页码「2」
预期结果：页码切到 2，列表显示第 11~20 条订单
实际结果：页码显示为 2，但列表数据仍是第 1~10 条
严重程度：高（用户无法查看历史订单，功能实质不可用）
优先级：高
附件：截图1 第1页列表；截图2 点击第2页后列表（内容相同）
```

**要点**：前置条件里的「订单 ≥ 11 条」是这条能被复现的关键。开发账号只有 3 条订单，永远复现不出来。

---

## 三条的共同教训

1. **复现步骤不能漏**。第一版三条全漏了，等于没提单。
2. **前置条件必须能调到触发状态**，不能自相矛盾（第一版 Bug 1 写成「登录成功」，却在登录页取验证码）。
3. **预期结果要写成「会提示什么 / 不会发生什么」**，不能写成一句形容词。
