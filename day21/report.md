# Day21 性能测试：用 JMeter 压一个接口

- 日期：2026-11-26
- 被测接口：http://127.0.0.1:8000/api/users
- 服务：day21/server.py（Python 标准库 ThreadingHTTPServer，查询 MySQL 的 users 表）
- 后端库：Docker 容器 mysql-test，映射 127.0.0.1:3307
- 压测工具：Apache JMeter 5.6.3，脚本 day21/day21.jmx

## 一、压测数据

第 0 轮 Loop Count=1，50 个请求分摊在 Ramp-up 的 5 秒里发完，Throughput 是发射速率不是处理能力，作废。
第 1 轮吞吐 3694/s 是错误计数速度：99.74% 的请求在建立 TCP 连接阶段就被拒绝，根本没到服务端。

## 二、三个核心读数（最终基线：第 5 轮）

- TPS：45.5/s
- P95：2308ms
- 错误率：0.00%

## 三、瓶颈区间结论

- 单请求真实耗时约 197ms（第 4 轮，10 并发）
- TPS 天花板约 45/s：并发从 10 加到 50，TPS 只从 44.8 到 45.5，P95 从 323ms 涨到 2308ms
- 即并发 10 附近就已到容量拐点，继续加并发只增加排队，不增加吞吐
- Little 定律核对：10 并发 44.8 × 0.197 ≈ 8.8；50 并发 45.5 × 1.052 ≈ 47.9，都与实际并发吻合

根因：每个请求新建一条 MySQL 连接（Windows → WSL → docker-proxy → 容器），连接握手开销占掉 197ms 的绝大部分，SQL 本身几乎不花时间。

## 四、加压后哪个指标先崩

- 修复连接复用前：错误率先崩。50 并发下错误率 99.74%，RT 反而降到 3ms，属于快速失败，不是扛住了
- 修复连接复用后：P95 先崩。323ms → 2308ms，错误率保持 0，请求都能完成，只是排队越来越久

## 五、做过的修复与验证

1. 现象矛盾：服务端日志全是 200，JMeter 报 99.74% 错误 → 失败请求没进到服务端，问题在连接层
2. 控制变量一：并发 50 → 10，错误率 99.74% → 7.36%，证明与并发量相关
3. 控制变量二：注释掉数据库查询换成 20 条假数据，TPS 涨到 1779.5，错误率反而 76.94% → 瓶颈不是数据库
4. 定位根因：BaseHTTPRequestHandler 默认 HTTP/1.0，每请求一条新 TCP 连接、不复用，60 秒 22 万条连接把端口和 listen 队列打爆
5. 修复：protocol_version 改为 "HTTP/1.1"（长连接复用）+ 补 Content-Length（告知响应体长度），错误率 7.36% → 0.00%

## 六、后续优化方向

1. MySQL 连接池：现在每请求新建连接，是 197ms 的主要来源；改成复用可把单请求降到几十毫秒
2. 接口直连本机 MySQL（3306）替代跨 WSL/docker-proxy 转发，减少一层网络开销
3. 正式压测改用命令行模式：jmeter -n -t day21.jmx -l result.jtl -e -o report，避免 GUI 自身成为瓶颈
