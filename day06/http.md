## 一、请求四部分

一次请求 = 寄一个快递。

| 四部分 | 快递里的角色 | 在 F12 里长什么样 |
|---|---|---|
| **方法** Method | 你要干什么：取件 / 寄件 / 改地址 / 退件 | 请求行第一个词：`GET`、`POST` |
| **URL** | 寄到哪个地址 | `https://api.xxx.com/v1/order?page=2` |
| **Header** | 快递单上的附加信息：你是谁、里面装的是什么 | `Cookie`、`Authorization`、`Content-Type` |
| **Body** | 包裹里装的东西 | `{"skuId":123,"count":2}` |

### 方法

| 方法 | 用途 | 判断口诀 |
|---|---|---|
| `GET` | 取数据 | 「看」用 GET |
| `POST` | 新建 | 「做」用 POST |
| `PUT` | 整体更新 | |
| `DELETE` | 删除 | |

GET 一般没有 Body，参数全拼在 URL 后面。

### URL 拆成四段

```
https:// api.xxx.com /v1/order ?page=2&size=10
  协议      域名       路径       查询参数
```

测试最常动手脚的地方是查询参数：`page` 改 0、`size` 改 99999。

### Header 四个必须认识的

| Header | 作用 | 漏了会怎样 |
|---|---|---|
| `Cookie` / `Authorization` | 身份凭证 | 401 / 403 的源头 |
| `Content-Type` | 告诉后端 Body 是什么格式 | 400 / 415，后端解析不了 |
| `User-Agent` | 客户端标识 | 部分接口按它返回不同内容 |
| 自定义字段（`X-Tenant-Id` 等） | 业务身份 | 最容易漏，漏了就查别人的数据 |

**Cookie 是密码级的东西**：拿到它的人不需要账号密码、不需要验证码，服务器就会认作本人。截图前必须打码，笔记里只写结构：

```
Cookie: SESSDATA=***; bili_jct=***; buvid3=***
```

`HttpOnly` 只防网页脚本读取，**防不了抓包**——传输层永远是明文。

## 二、7 个状态码

总规则：**4 开头怪自己，5 开头怪开发**。

| 码 | 含义 | 场景比喻 |
|---|---|---|
| `200` | OK | 门开了 |
| `302` | 重定向 | 这门搬走了，去新地址 |
| `400` | 请求参数有问题 | 申请单填错了 |
| `401` | 未认证 | 没带身份证 |
| `403` | 无权限 | 带了身份证，但不是 VIP |
| `404` | 资源不存在 | 走错门了 |
| `500` | 服务端异常 | 屋里着火了 |

**401 vs 403 的区别（面试常考）**

- 401 = 不知道你是谁 → 没登录、token 过期、token 伪造
- 403 = 知道你是谁，但不让你进 → 登录了但权限不够

### 测试视角：什么时候该警惕

| 你做了什么 | 正常应该 | 如果返回 500 |
|---|---|---|
| 少传必填参数 | 400 | 后端没做参数校验，把异常直接抛出去了 → 提 bug |
| 不带 token 请求 | 401 | 鉴权中间件漏了接口 → 安全漏洞 |
| 普通账号调管理员接口 | 403 | 权限校验没做 → 高危 |
| 请求已删除的商品 | 404 或业务提示 | 空指针没判 → 提 bug |

**核心判断**：故意传错参数却收到 500 而不是 400，就是后端缺校验。
反过来，看到 4xx 先检查自己是不是构造错了，别急着提单。

## 三、双层状态：接口测试最重要的一条认知

一次接口返回有**两层状态**：

| 层 | 看什么 | 例子 |
|---|---|---|
| HTTP 层 | 状态码 | 200 |
| 业务层 | 响应体里的 code | `{"code": 0}` = 成功 |

**HTTP 200 不等于业务成功。**

很多系统会这么返回：

```json
HTTP 200
{"code": 10001, "message": "登录已过期，请重新登录"}
```

技术层面处理成功了，业务层面失败了。只看状态码必然漏 bug。

**所以接口用例的预期要写两层：**

```
HTTP 状态码 = 200 且 返回体 code = 0
```

## 四、实操记录：抓 B 站搜索联想接口

### 抓包过程

1. 打开 `bilibili.com`，F12 → **Network / 网络**
2. 过滤按钮点 **Fetch/XHR**（只看接口请求，排除 js / 图片）
3. 点 🚫 清空
4. 在搜索框输入「测试开发」

**Fetch/XHR 是什么**：浏览器在后台悄悄发请求、拿数据的技术，分 `XHR`（老）和 `Fetch`（新）两种。特点是**页面不刷新**，只拿数据回来自己画。

区别要点：

- 打开网页整页刷新 → 落在 `Doc`
- 图片加载 → 落在 `Img`
- 打字出候选词、页面没动 → 落在 **`Fetch/XHR`**
- 测试要盯这里，因为**绝大多数 bug 藏在接口层**，页面上看不见

### 抓到的请求

```
名称：suggest?highlight=0&term=...
方法：GET
状态：200 OK
调用方：index-7f2326a6.js
```

打四个字就发了四次请求——**输入频率也值得测试**。

### 实验一：正常查询

```
URL:  https://api.bilibili.com/x/web-interface/suggest?highlight=0&term=c&...
方法: GET
结果: HTTP 200
返回: {"code":0,"message":"OK","ttl":1,"data":{...},"total_count":10}
```

`code: 0` = 业务成功，`data` 里是候选词列表。

### 实验二：空值查询

把 `term=c` 改成 `term=`：

```
结果: HTTP 200
返回: {"code":3,"message":"3","ttl":1}
```

**对比两次：**

| 请求 | HTTP | 业务 code | 结果 |
|---|---|---|---|
| `term=c` | 200 | 0 | 成功 |
| `term=`（空） | 200 | 3 | 失败 |

**两次 HTTP 都是 200，但一次成功一次失败。**

这张表就是「光看状态码判断不出接口对不对」的实证。

### 顺带发现的两个小缺陷

1. **错误提示不可读**：`message: "3"` 返回给调用方毫无意义，规范写法应是 `"keyword 不能为空"`
2. **返回体结构不稳定**：成功时有 `data` / `total_count` / `stoken`，失败时只剩 `code` / `message` / `ttl`。调用方直接读 `data.result` 就会空指针。规范做法是失败时也保留 `data: null`

## 五、GET 请求可以直接在浏览器地址栏发

把那条 URL 粘到浏览器新标签页回车，就能拿到 JSON。

因为 GET 把参数全写在 URL 上、没有 Body。**POST 就不行**——它有 Body，浏览器地址栏装不下。

这也是「看数据用 GET、做操作用 POST」的现实原因。

## 六、Postman 重放

### 结果

```
方法：GET
状态：200 OK
耗时：489 ms
大小：883 B
返回：{"code":0,"message":"OK","ttl":1,"data":{...}}
```

重放成功，和浏览器里看到的完全一致。今天的验收标准达成。

### Postman 的核心价值：参数表格化

Postman 自动把 URL 里 `?` 后面的内容拆成了一张表格：

| Key | Value |
|---|---|
| `highlight` | 0 |
| `term` | c |
| `spmid` | 333.1007 |
| `web_location` | 333.1007 |
| `x-bili-locale-json` | `%7B%22c_locale%22...` |
| `x-bili-device-req-json` | `%7B%22platform%22...` |
| `w_rid` | 527a164fe38024da6f516682c4f58f68 |
| `wts` | 1794922815 |

这张表就是 URL 里 `?page=2&size=10` 那一段被逐项拆开的结果。

**好处**：改参数直接改表格，不用在几十个字符的长 URL 里找位置、改错 `&`。做几十次实验时这个差别非常大。

### 注意 `w_rid` 和 `wts`

这两个不是业务参数，是 B 站请求签名：

- `wts` 是时间戳
- `w_rid` 是服务端算出来的签名

**签名类参数有时效**。放几小时后重放，旧签名就失效，接口会返回 `412`（风控拦截）。这是「昨天还能跑的请求今天跑不通」最常见的原因——不是接口变了，是签名过期了。

### `489 ms` 这个数也要看

接口测试不只关心「对不对」，还关心「快不快」。单次 489 ms 说明还行；但后面 Day 19 用 JMeter 压测时，要看的是**并发时**的响应时间（TPS / P95 / P99），那是另一回事。

## 小结

> 一个请求四样东西：**干什么用方法、寄到哪用 URL、身份在 Header、内容在 Body**。
>
> **4 开头怪自己，5 开头怪开发。**
>
> **HTTP 200 不代表业务成功**——接口预期必须写成两层：状态码 200 且 code = 0。

### 今天最容易混的三个点

1. 401 和 403：401 是没带身份，403 是带了身份但没权限
2. HTTP 状态码和业务 code：前者是「传输通不通」，后者是「业务成不成」
3. GET 和 POST：GET 参数在 URL，POST 参数在 Body

### 今日新词记录

- 接口 / API：程序之间对话的约定
- Fetch/XHR：浏览器后台取数据的技术，页面不刷新
- 双层状态：HTTP 状态码 + 业务 code
- 幂等：同一个请求发多次，结果和一个一样（POST 通常不幂等，这也是"连点两次提交订单"会出两个订单的根源）
