## 一、AI 生成用例到底解决什么

| 它解决 | 它不解决 |
|---|---|
| 广度：从零想到 10 个场景的 40 分钟 | 质量：哪条能用、哪条是错的 |
| 规模：200 个接口批量出草稿 | 判断：边界值该取哪些、断言该写什么 |

**结论：它给 60 分的起点，人把它抬到 90。** 只做"生成"这一步没有价值，价值在审稿和转执行。

## 二、prompt 六段结构（缺一段就不稳）

| 段 | 写什么 | 缺了会怎样 |
|---|---|---|
| 1 角色 | "你是 5 年经验的测试工程师" | 写成产品经理口吻，全是需求描述 |
| 2 契约 | 接口/参数/返回/业务规则 + 错误码表，**原样贴** | 它自己编参数，产生幻觉 |
| 3 覆盖分配 | 分维度给数量：正常 3 / 异常 3 / 边界 3 / 安全 1 | 10 条全挤在一个等价类 |
| 4 约束 | 每条只测一个点、能独立执行、**预期必须是具体数字** | 出现"校验不通过"这种没法断言的话 |
| 5 格式 | Markdown 四列表格，表头固定 | 输出像散文，没法转脚本 |
| 6 样例 | 一条完整的范样例（不计入数量） | 颗粒度失控，一条塞五个步骤 |

**为什么样例比形容词有效**：说"写得专业点"它不知道什么叫专业；给一条完整样例，它立刻知道步骤写三步、预期写一句话。**样例锚定的是格式和颗粒度，不是内容。**（面试高频）

**约束里最狠的一句**：`预期必须写出 HTTP 状态码和 code 的具体数字，禁止"校验不通过""拒绝登录"这类无法断言的描述`。

## 三、AI 生成用例的四类通病（审稿 checklist）

1. **幻觉**：编出不存在的参数、路径、返回码
2. **分布畸形**：10 条里 6 条同一个等价类，换个输入字符串就交差
3. **预期不可断言**：写"校验不通过""拒绝登录"，没法写进 `assert`
4. **数字算错**（最危险）：`abcdefgh1234_abcd` 它说是 16 位，实际 17 位

**第 4 类最隐蔽**：格式完美、措辞专业、数字全错，抄进脚本才炸。

> 铁律：**凡是长度、数量、边界值，一律用 `len()` 算，不要用眼睛读。**

```python
for s in ["abcdefgh1234_abcd"]:
    print(len(s), s)   # 17
```

## 四、用例是"拆"出来的，不是"想"出来的（今天真正的短板）

### 三步法

**第一步：需求 → 规则清单。** 一句一条，每条可判定通过/不通过。登录接口拆成三条：

- 规则 A：username 长度 3–16，只能是字母/数字/下划线
- 规则 B：password 长度 8–20，必须同时含字母和数字
- 规则 C：同一账号连续失败 5 次锁 30 分钟

**第二步：每条规则只拆三类输入。**

- 有效：规则允许的典型值
- 无效：规则不允许的典型值
- 边界：恰好在线内一个、线外差一个（下限/上限各一对）

**第三步：排成表格核对。** 规则 × 类别，格子里填具体值，**空格就是漏掉的用例**。

### 规则 B 的完整 7 条（示例）

| 类别 | 值 | 期望 |
|---|---|---|
| 长度下限达标 | `a1234567`（8 位） | 0 |
| 长度上限达标 | `Abc12345678901234567`（20 位） | 0 |
| 下限差一 | `a123456`（7 位） | 1002 |
| 上限超一 | `Abc123456789012345678`（21 位） | 1002 |
| 组成有效 | `Abc12345` | 0 |
| 组成·全字母 | `abcdefgh` | 1002 |
| 组成·全数字 | `12345678` | 1002 |

**一条规则 7 条用例，是数出来的不是想出来的。** AI 那版只给了 2 条（8 位、20 位），另 5 格全空。

### 边界用例的断言技巧（专业写法）

边界用例**不要断言"登录成功"**，断言 `code=1001`：

- 返回 `1001` → 格式校验已通过，进入业务判断才发现用户不存在，说明边界值测到了点上
- 返回 `1002` → 长度校验没过，边界值根本没测到

**用错误码反证"校验通过"**，比断言成功更有信息量。边界用例的用户通常不存在，断言"成功"必然失败，这是 AI 最常犯的逻辑错。

## 五、把用例变成能跑的代码

### 结构

```python
import pytest
from fake_login import fake_login

CASES = [
    ("TC-01", "test01", "abc12345", 0),
    ("TC-07", "abcdefgh1234_abc", "Abc12345", 1001),
    # ...
]

@pytest.mark.parametrize("case_id, username, password, expect_code", CASES)
def test_login(case_id, username, password, expect_code):
    result = fake_login(username, password)
    assert result["code"] == expect_code, f"{case_id} 期望 {expect_code} 实际 {result['code']}"
```

### 三个必须对齐的点

1. 元组是 4 个值，顺序 `编号、用户名、密码、期望码`
2. `parametrize` 的字符串顺序与元组一致，错一个全乱
3. **assert 的失败信息必须带 `case_id`**，否则 3 条红了你不知道是哪条

### 校验顺序决定错误码

`fake_login` 里先校验格式、再校验业务。顺序反了，TC-07/TC-08 的 `1001` / `1002` 就全不成立。

```python
import re

USERS = {"test01": "abc12345", "test_02": "def67890", "test03": "Abc12345"}

def fake_login(username, password):
    if not re.fullmatch(r"[A-Za-z0-9_]{3,16}", username):
        return {"code": 1002, "msg": "参数格式不合法"}
    if not (8 <= len(password) <= 20):
        return {"code": 1002, "msg": "参数格式不合法"}
    if not re.search(r"[A-Za-z]", password):
        return {"code": 1002, "msg": "参数格式不合法"}
    if not re.search(r"[0-9]", password):
        return {"code": 1002, "msg": "参数格式不合法"}
    if username not in USERS or USERS[username] != password:
        return {"code": 1001, "msg": "用户名或密码错误"}
    return {"code": 0, "token": "fake-token-" + username, "msg": "登录成功"}
```

- `fullmatch` 校验**整体字符集**（整个串只能这些字符）
- `search` 校验**包含关系**（串里得有字母/数字）
- `username not in USERS or ...` 的 `or` 短路，防止 `KeyError`

## 六、AI Coding 工具 vs 纯聊天

| | 纯聊天 | AI Coding（Cursor / Claude Code / Codex） |
|---|---|---|
| 上下文 | 你贴给它 | 它自己读整个项目目录 |
| 产出 | 一段文本，你复制粘贴 | 直接改你本地文件 |
| 验证 | 不能，你跑完再把报错贴回去 | 能，它执行命令、看报错、自己改 |
| 适合 | 写用例、评审、讲概念 | 改代码、跨文件重构、写测试并跑通 |

**一句话：聊天是"你喂上下文，它给文本"；Coding 是"它在你的项目里看文件、改文件、跑命令"。差别不在模型，在闭环发生在谁那里。**
